## ب — مخالفات معمارية

### B1. طبقة العرض تستورد طبقة البيانات مباشرة (خرق اتجاه الاعتماد)
Clean Architecture تفرض `presentation → domain ← data`. هذه الملفات تقفز فوق `domain`:
- `lab/presentation/pages/lab_notifications_page.dart`
- `lab/presentation/widgets/dashboard/lab_dashboard_orders_table.dart`
- `warehouse/presentation/widgets/notifications/warehouse_notifications_content.dart`

(الثلاثة نفسها في A1 — الخرق المعماري هو ما سمح بتسرّب الـ mock إلى الشاشة.)

### B2. تجريد ميت: `ApiResult` و`Either` معرَّفان ولا يُستعملان
`lib/core/network/api_result.dart` يستورد `package:dartz` ويعرّف `ApiResult`. البحث في كامل `lib` يعطي: **صفر مستهلك** خارج `api_result.dart` و`failure.dart` نفسيهما. أي أن حزمة `dartz` كاملة موجودة لأجل تجريد لا يستدعيه أحد، ومعالجة الأخطاء الفعلية تجري بـ `try/catch` في كل مكان بدلاً منه.

### B3. `MockSystemCubit` هو مصدر الحقيقة لدور المستخدم في الإنتاج
اسمه وتوثيقه يقولان صراحةً: *«في غياب الـ Backend… عند جاهزية الـ API يتم استبدال هذا Cubit بـ AuthCubit الذي يقرأ الدور من JWT»*. لكنه اليوم مربوط في قلب التطبيق:
`main.dart:124,142` · `injection_container.dart:104` · `app_shell_layout.dart:352` · `system_selection_page.dart:452` · `core/auth/auth_models.dart:22`

والباك آند جاهز والأدوار حقيقية (سجلّ المشروع يؤكّد ربط `RouteGuards` بالدور الفعلي). فإمّا أنه صار حالةً حقيقية باسم مضلِّل، أو أنه بقي محاكاةً تتحكّم بالتوجيه — وكلا الاحتمالين عيب.

### B4. لا طبقة `use cases` إطلاقاً
لا مجلد `usecases` في أي ميزة؛ الـ Cubit ينادي الـ Repository مباشرة. هذا خيار مشروع ومقبول، **لكن** المشروع يعلن Clean Architecture ببنية `data/domain/presentation` كاملة، ولا يوثّق حذف الطبقة. مشرف صارم سيقرأ هذا نقصاً لا قراراً.

### B5. البنية غير متّسقة بين الميزات
| الميزة | `domain/entities` | `data/models` | `data/mock` |
|---|---|---|---|
| auth | ✗ | ✗ | ✗ |
| lab | ✓ | ✓ | ✓ |
| warehouse | ✓ | ✗ | ✓ |
| profile | ✓ | ✗ | ✗ |

أربع ميزات بأربع بنى مختلفة.

### B6. نمط الحالة غير متّسق بين النظامين
- **lab:** 8 Cubits، لكلٍّ منها ملف `_state.dart` منفصل (8/8).
- **warehouse:** 6 Cubits، واحد فقط له ملف state (`materials_state.dart`) — والخمسة الباقون (`inventory`, `purchase_invoices`, `stock`, `warehouse_reports`, `warehouse_requests`) يعرّفون حالتهم داخلياً.

### B7. صفحات تدير حالة شبكة بـ `setState` بلا Cubit
لا Cubit مقابل لـ: `lab_settings_page` · `warehouse_dashboard_page` · `warehouse_notifications_page` · `warehouse_settings_page`. هذه بقايا هجرة Cubit غير المكتملة، وهي نفسها الشاشات التي تعرض mock في A1.
