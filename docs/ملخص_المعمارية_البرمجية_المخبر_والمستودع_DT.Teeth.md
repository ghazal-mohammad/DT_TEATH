المعمارية البرمجية لتطبيقات النظام (Software Architecture)
نظام DT.Teeth — تطبيق إدارة المخبر والمستودع (Flutter Web)

1. نظرة عامة على النظام والمعمارية

تطبيق إدارة المخبر والمستودع هو منصة ويب مستقلة ضمن منظومة DT.Teeth، تخدم رئيس المخبر ورئيس المستودع (مع إمكانية دخول المدير لاختيار النظام). يعتمد التطبيق على معمارية Client-Server تفصل الواجهة الأمامية عن الخدمات الخلفية المركزية، ولا يتصل بقاعدة البيانات مباشرة بل عبر RESTful APIs.

يغطي التطبيق: المصادقة وتفعيل الحساب وإعادة تعيين كلمة المرور، اختيار النظام، طلبات التعويضات السنية ومراحلها، الفنيين والمنتجات ومخزون المخبر وطلبات المواد، إدارة مواد المستودع والطلبات والفواتير والتقارير والإشعارات والملف الشخصي.

المكدس التقني المعتمد:

الطبقة	التقنية
Frontend	Flutter Web (Dart) + Material 3 + flutter_screenutil
إدارة الحالة	flutter_bloc (Cubit) + equatable
التنقل والصلاحيات	go_router + RouteGuards حسب الدور
حقن الاعتماديات	GetIt (تسجيل يدوي)
HTTP Client	Dio + Bearer Token (متوافق مع Laravel Sanctum)
التخزين المحلي	flutter_secure_storage (التوكن) + shared_preferences (كاش / إعدادات / Outbox)
Backend	Laravel 11 + Sanctum
Database	MySQL
الألوان الأساسية	#1A1C4E (أزرق داكن) + #E9ECFB (خلفية فاتحة) + عائلة auth الكحلية (#141455 / #5959B3)

الأدوار الأساسية في هذا التطبيق:
• Lab Manager: طلبات المخبر، الفنيين، المنتجات، المخزون، طلبات المواد، التقارير.
• Warehouse Manager: المواد، الطلبات، الفواتير، حركة المخزون، التقارير.
• Admin: الوصول لكلا النظامين عبر شاشة اختيار النظام بعد تسجيل الدخول.

2. الفكرة الأولى: تنظيم Feature-First حسب النظام

بدلاً من تقسيم المشروع حسب النوع التقني فقط (pages / widgets / services)، نُظّم الكود أولاً حسب الميزة/النظام، ثم الطبقات داخل كل ميزة.

مثال على الهيكل:
lib/features/auth/          ← المصادقة وتفعيل الحساب
lib/features/lab/           ← ميزات المخبر
lib/features/warehouse/     ← ميزات المستودع
lib/features/profile/       ← الملف الشخصي المشترك
lib/core/                   ← شبكة، راوتر، ثيم، أوفلاين، DI
lib/shared/widgets/         ← مكونات واجهة مشتركة (زر، جدول، نماذج، تخطيط...)

كل ميزة تحتفظ داخلياً بـ:
presentation/  (صفحات + Cubits)
domain/        (Entities + واجهات Repository)
data/          (Remote DataSource + تنفيذ Repository)

لماذا هذه الفكرة مهمة؟
• عزل منطق المخبر عن المستودع مع مشاركة المصادقة والملف الشخصي والمكوّنات المشتركة.
• سهولة الصيانة: تعديل شاشات طلبات المخبر لا يمس فواتير المستودع.
• قابلية التوسع: إضافة نظام فرعي جديد تتم بإضافة feature دون إعادة هيكلة كاملة.
• توافق مباشر مع توزيع مهام الرسالة (Flutter Web للمخبر والمستودع).

3. الفكرة الثانية: Clean Architecture مُكيَّفة لـ Flutter

طُبّقت مبادئ Clean Architecture بصورة عملية ومتكيّفة مع حجم المشروع، دون فرض طبقة Use Cases منفصلة غير مستخدمة فعلياً. الطبقات المنطقية هي:

3.1 طبقة العرض (Presentation Layer)
مسؤولة عن العرض والتفاعل. تشمل الصفحات والـ Widgets، ونظام الثيم (فاتح/داكن)، ودعم RTL، ومكوّنات مشتركة من shared/widgets. إدارة الحالة عبر Cubit: الواجهة تقرأ الحالة وتعيد البناء عند التغيّر، ولا تستدعي Dio مباشرة.

3.2 طبقة المجال (Domain Layer)
تمثل قواعد النموذج والعقود:
• Entities لنماذج العمل (طلبات، مواد، فواتير...).
• واجهات Repository مجرّدة بلا اعتماد على Dio أو Flutter UI.
هذا يفصل قواعد البيانات المتوقعة عن تفاصيل الشبكة والتخزين.

3.3 طبقة البيانات (Data Layer)
مسؤولة عن التواصل مع الخادم والتخزين المحلي:
• Remote DataSource عبر Dio ونقاط ApiEndpoints المتوافقة مع Laravel.
• تنفيذ Repository يحوّل JSON إلى Entities جاهزة للواجهة.
• طبقات كاش/طابور كتابة عند انقطاع الشبكة (PersistentCache + Outbox).

تدفق العمل النموذجي:
UI → Cubit → Repository (واجهة) → Remote/Local DataSource → Laravel API
ثم العودة: Response → Mapping → State → UI

4. الفكرة الثالثة: إدارة الحالة بـ Cubit

بدل الاعتماد على Redux أو إدارة حالة عملاقة واحدة، اعتُمدت استراتيجية مناسبة لطبيعة البيانات:

نوع الحالة	الأداة	الاستخدام
حالة الميزات (Server/UI)	Cubit + flutter_bloc	طلبات، مواد، فواتير، مصادقة، لوحات
حالة التطبيق العامة	ThemeCubit / LocaleCubit / TextScaleCubit	الثيم، اللغة، مقياس النص
جلسة المستخدم	CurrentUser + Secure Storage	الدور والتوكن بعد الدخول
التغذية الراجعة	Glass Toast / رسائل حالة Cubit	نجاح، خطأ، تحميل

لماذا Cubit؟ لأنه أبسط من Bloc القائم على Events في أغلب الشاشات التشغيلية، ويحافظ على فصل المنطق عن الواجهة، مع قابلية اختبار عالية عبر bloc_test.

5. الفكرة الرابعة: التنقل الموجَّه بالصلاحيات (Route Guards)

التنقل عبر go_router مع مسارات واضحة للمخبر والمستودع والمصادقة. بعد تسجيل الدخول يُحدَّد الوجهة حسب الدور:
• labManager → مسارات /lab/*
• warehouseManager → مسارات /warehouse/*
• admin → /system-selection ثم اختيار النظام

المسارات العامة (splash، email، verify، set-password، login) تبقى متاحة بلا توكن. هذا يحقق فصل الواجهات دون تطبيقين منفصلين بالكامل، مع الحفاظ على نفس المكدس والمكوّنات المشتركة.

تدفق المصادقة النموذجي:
Splash → إدخال البريد → رمز التحقق → تعيين كلمة المرور / تسجيل الدخول → (اختيار النظام للمدير) → لوحة المخبر أو المستودع

6. الفكرة الخامسة: الشبكة، الحقن، والأمان على العميل

• DioClient يضيف Authorization: Bearer تلقائياً، ويفرض HTTPS خارج التطوير، ويعالج 401 بمسح الجلسة وإعادة التوجيه لتسجيل الدخول.
• التوكن يُحفظ في flutter_secure_storage وليس في نص واضح داخل الكود.
• GetIt (sl) يربط Dio ← DataSources ← Repositories ← Cubits عند الحاجة، بتسجيل يدوي واضح وقابل للتتبع.
• حماية إضافية على مستوى التطبيق تشمل مهلة خمول ومكوّنات خصوصية للواجهة حيث يلزم.

7. الفكرة السادسة: العمل شبه دون اتصال (Online-first + Cache/Outbox)

التطبيق Online-first مع دعم كاش قوي وليس Offline-first كاملاً:
• قراءة: PersistentCache يحتفظ بآخر قوائم معروفة لعرضها عند انقطاع الشبكة.
• كتابة: Outbox يصفّ العمليات الصادرة ويعيد مزامنتها عند عودة الاتصال.
• التخزين المحلي عبر shared_preferences (بدون Hive)، بما يتوافق مع حجم البيانات التشغيلية لهذا التطبيق.

بعد الكتابة الناجحة عبر الشبكة: تحديث الحالة، إبطال/تحديث الكاش المرتبط، وإظهار رسالة نجاح للمستخدم.

8. الفكرة السابعة: الثيم، الترجمة، وRTL كـ Cross-Cutting Concerns

• ثيم موحّد في core/theme (AppColors, AppTextStyles, AppSizes) مع وضع فاتح وداكن.
• i18n عبر ملفات ARB (عربي/إنجليزي) وLocaleCubit؛ العربية افتراضية مع RTL كامل عبر Directionality.
• خطوط Cairo وTajawal مضمَّنة محلياً لدعم العربية على الويب.
• هذا يفصل المحتوى عن الكود ويوحّد المصطلحات الطبية/التشغيلية عبر شاشات المخبر والمستودع.

9. الخلاصة والفوائد

المعمارية البرمجية لتطبيق المخبر والمستودع في DT.Teeth تعتمد على سبعة أعمدة رئيسة:
• Feature-First حسب النظام (lab / warehouse / auth / profile).
• Clean Architecture مُكيَّفة (عرض → مجال → بيانات) بدون طبقة Use Cases زائدة.
• Cubit لإدارة الحالة وفصلها عن الواجهة.
• go_router + حراسة مسارات حسب الدور.
• Dio + Bearer/Sanctum مع حقن GetIt وأمان جلسة على العميل.
• كاش وقائمة انتظار كتابة لدعم العمل عند ضعف/انقطاع الشبكة.
• ثيم موحّد + i18n وRTL كامل.

هذه المعمارية تحقق التوازن بين الأداء التشغيلي، ووضوح الصلاحيات، وسهولة الصيانة، وقابلية التوسع، وتوفر أساساً مناسباً لأي توسعات لاحقة (ميزات مخبرية/مستودعية إضافية أو تعزيز أوفلاين أقوى) مع الإبقاء على التكامل مع Backend المركزي لمنظومة DT.Teeth.
